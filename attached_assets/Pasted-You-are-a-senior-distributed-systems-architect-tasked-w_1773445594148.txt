You are a senior distributed-systems architect tasked with upgrading the FounderConsole platform to a production-grade scalable architecture.

The existing codebase already contains:

- FastAPI backend
- React frontend
- PostgreSQL database
- Digital Twin service
- Monte Carlo simulation engine
- AI Copilot multi-agent system
- 33+ data connectors
- Truth Scan pipeline

However the system has major architectural problems:

- no caching layer
- no async job queue
- simulations run in request cycle
- token revocation stored in memory
- excessive JSON columns
- connector syncs run inline
- no websocket layer
- UI navigation complexity
- too many pages
- no observability
- no backup strategy

Your task is to redesign the system architecture and generate implementation scaffolding WITHOUT breaking existing features.

--------------------------------

PHASE 1 — INFRASTRUCTURE LAYER

Introduce Redis as the central infrastructure service.

Redis responsibilities:

1. cache layer
2. job queue
3. rate limiter
4. token revocation store
5. websocket pub/sub

Implement Redis integration in FastAPI.

Create modules:

server/infrastructure/
    redis_client.py
    cache.py
    queue.py
    pubsub.py

Caching targets:

- company_state
- KPI calculations
- digital twin state
- scenario templates
- benchmark data

Use cache invalidation when:

- financial records change
- simulation finishes
- connector sync completes


--------------------------------

PHASE 2 — JOB QUEUE SYSTEM

Replace database polling workers with a Redis-backed job queue.

Implement queues:

simulation_queue
connector_sync_queue
ai_tasks_queue
forecast_queue
alert_queue

Create worker services:

server/workers/
    simulation_worker.py
    connector_worker.py
    ai_worker.py
    forecasting_worker.py

Workers must support:

- concurrency
- retries
- exponential backoff
- dead letter queue
- job status updates

Simulations must run only in simulation_worker.


--------------------------------

PHASE 3 — WEB-QUEUE-WORKER ARCHITECTURE

Refactor request flow.

Current flow:

API → run simulation → return result

New flow:

API
  → enqueue simulation job
  → return job id

Worker
  → process simulation
  → store results
  → publish websocket update

Frontend subscribes to job updates.
