## BUG 1: NLP Scenario Parsing — CRITICAL (Core Product Broken)

### What's broken
When a user types a natural language simulation like "What happens if our shipping costs increase 25%?", the simulation engine runs but **does NOT modify any variables**. The "Scenario Inputs vs Baseline" section shows **"No changes from baseline"** for every simulation. The AI narrative is generic and never mentions the scenario topic.

### Reproduction
1. Go to `/simulate`
2. Type: "What happens if our shipping costs increase 25% due to fuel price hikes?"
3. Click Simulate
4. Check "Scenario Inputs vs Baseline" → shows "No changes from baseline"
5. Check AI narrative → generic text, no mention of shipping or fuel
6. Repeat with "What happens if COD return rates spike from 15% to 35%?" → same result
7. Repeat with "What happens if a competitor launches free shipping and we lose 20% of customers?" → same result

### Evidence
- 5 rounds of testing, 15+ simulations — NLP has NEVER successfully parsed an industry-specific scenario
- Only generic financial terms work (e.g., "cut marketing 30%" → correctly reduces burn)
- Quick scenario pills (pre-built buttons) work fine — the issue is in the NLP text → variable mapping

### Root cause analysis
The NLP parser likely uses a pattern-matching or keyword-extraction approach that only recognizes a limited set of financial terms: "marketing", "hiring", "prices", "burn", "churn", "fundraise". It does NOT recognize:
- Industry terms: "shipping costs", "COD returns", "carrier rates", "fulfillment", "RTO", "return rate"
- Competitive terms: "competitor", "customer loss", "market share"
- Operational terms: "fuel price", "warehouse", "logistics"

When the NLP fails to extract variables, the simulation runs on unmodified baseline data — producing identical results regardless of what the user typed.

### Fix approach

**Option A: Structured LLM extraction (recommended)**

Replace the keyword-based parser with an LLM call that extracts structured variable changes from the user's text:

```python
# In your simulation preprocessing / scenario parser

SYSTEM_PROMPT = """You are a financial scenario parser for a startup simulation engine.

Given a user's natural language scenario description and their current financial baseline,
extract the specific variable changes that should be applied to the Monte Carlo simulation.

Available variables you can modify:
- revenue_growth_rate (current: {current_growth}%) — change in percentage points
- monthly_burn_change (current: ${current_burn}) — percentage change to burn rate
- churn_rate (current: {current_churn}%) — new absolute churn rate
- gross_margin (current: {current_margin}%) — new absolute gross margin
- fundraise_amount — dollar amount of new funding
- customer_count_change — percentage change in customer count
- cac_change — percentage change in customer acquisition cost
- opex_change — percentage change in operating expenses

Rules:
1. Map the user's scenario to ONE OR MORE variable changes
2. "shipping costs increase 25%" → opex_change: +25 (shipping is an operating expense)
3. "lose 20% of customers" → customer_count_change: -20, revenue_growth_rate: -20
4. "COD returns spike to 35%" → gross_margin: reduce by ~15pp (returns eat margin), opex_change: +10 (reverse logistics cost)
5. "competitor launches free shipping" → churn_rate: increase by 3-5pp, revenue_growth_rate: -10 to -15
6. If the scenario is NEGATIVE, you MUST modify variables in a negative direction
7. If you cannot map the scenario, return clarifying_question instead

Return JSON:
{
  "parsed_variables": {
    "variable_name": new_value_or_delta,
    ...
  },
  "confidence": "high" | "medium" | "low",
  "reasoning": "brief explanation of mapping",
  "clarifying_question": null | "question string if ambiguous"
}
"""

async def parse_scenario(user_text: str, baseline: dict) -> dict:
    prompt = SYSTEM_PROMPT.format(
        current_growth=baseline["growth_rate"],
        current_burn=baseline["monthly_burn"],
        current_churn=baseline["churn_rate"],
        current_margin=baseline["gross_margin"],
    )

    response = await openai_client.chat.completions.create(
        model="gpt-4o",
        messages=[
            {"role": "system", "content": prompt},
            {"role": "user", "content": user_text}
        ],
        response_format={"type": "json_object"},
        temperature=0.1  # Low temp for consistent extraction
    )

    return json.loads(response.choices[0].message.content)
```

## BUG 2: Score Calibration — All Scenarios Return 8/10 GO

### What's broken
Every simulation returns 8/10 GO regardless of scenario severity. A founder asking "What happens if a competitor takes 20% of our customers?" gets the same 8/10 GO as "What happens if we cut costs 30%?" This makes the decision engine useless — it always says GO.

### Reproduction
1. Run any 3 different simulations (positive, neutral, negative)
2. All return 8/10 GO
3. The "YOUR ANSWER" narrative always says "Move forward" or "Launch it"

### Root cause
The scoring function likely doesn't weight the DIRECTION of the scenario. Since NLP isn't modifying variables (Bug 1), all simulations run on baseline data and produce similar results → similar scores. But even when variables ARE modified (via quick pills), scores don't differentiate enough.

### Fix approach

Implement a scoring rubric that considers survival probability and runway change:

```python
def calculate_decision_score(simulation_result: dict, baseline: dict) -> dict:
    """
    Calculate a calibrated 1-10 decision score.

    Scoring rubric:
    - 1-3: NO-GO (survival drops below 70% OR runway drops >50%)
    - 4-5: CAUTION (survival 70-85% OR runway drops 20-50%)
    - 6-7: CONDITIONAL GO (survival 85-95% OR runway drops 5-20%)
    - 8-9: GO (survival >95% AND runway drops <5%)
    - 10: STRONG GO (survival >99% AND runway increases)
    """

    p50_runway_before = baseline["runway_months"]
    p50_runway_after = simulation_result["p50_runway"]
    survival_18m = simulation_result["survival_18m"]
    p10_runway = simulation_result["p10_runway"]

    runway_change_pct = (p50_runway_after - p50_runway_before) / max(p50_runway_before, 1) * 100

    # Start with base score of 5
    score = 5.0

    # Survival probability impact (heaviest weight)
    if survival_18m >= 0.99:
        score += 2.0
    elif survival_18m >= 0.95:
        score += 1.5
    elif survival_18m >= 0.85:
        score += 0.5
    elif survival_18m >= 0.70:
        score -= 1.0
    elif survival_18m >= 0.50:
        score -= 2.5
    else:
        score -= 4.0  # <50% survival = very bad

    # Runway change impact
    if runway_change_pct > 20:
        score += 2.0
    elif runway_change_pct > 5:
        score += 1.0
    elif runway_change_pct > -5:
        score += 0.0  # Neutral
    elif runway_change_pct > -20:
        score -= 1.0
    elif runway_change_pct > -50:
        score -= 2.0
    else:
        score -= 3.0  # Runway cut by 50%+ = terrible

    # P10 downside risk adjustment
    if p10_runway < 12:
        score -= 1.0
    elif p10_runway < 6:
        score -= 2.0

    # Clamp to 1-10
    score = max(1, min(10, round(score)))

    # Determine verdict
    if score <= 3:
        verdict = "NO-GO"
    elif score <= 5:
        verdict = "CAUTION"
    elif score <= 7:
        verdict = "CONDITIONAL GO"
    else:
        verdict = "GO"

    return {
        "score": score,
        "verdict": verdict,
        "risk_score": calculate_risk_subscore(simulation_result),
        "reward_score": calculate_reward_subscore(simulation_result, baseline),
        "capital_efficiency": calculate_capital_efficiency(simulation_result),
        "survival_impact": survival_18m - baseline.get("survival_18m", 1.0),
    }
```

**Key principle:** A simulation that reduces runway by >20% or drops survival below 85% should NEVER get an 8/10 GO. The scoring must be DIRECTIONAL.

## BUG 6: Counter-Move "Cut Costs 20%" Shows Negative Runway Impact

### What's broken
The "Cut Costs 20%" counter-move shows a NEGATIVE runway delta of -0.3 months. Cutting costs should EXTEND runway, not reduce it.

### Root cause
The counter-move is likely being compared against the wrong baseline. If the comparison is `counter_move_runway - previous_simulation_p50` instead of `counter_move_runway - current_baseline_runway`, and the previous simulation had a higher P50 than the baseline, the delta appears negative.

### Fix

```python
def calculate_counter_move_impact(counter_move_result: dict, baseline: dict) -> dict:
    """
    Always compare counter-move outcomes against the COMPANY BASELINE,
    not against the current simulation's P50.
    """
    baseline_runway = baseline["dashboard_runway"]  # Use the 60.0 month dashboard value

    return {
        "runway": counter_move_result["p50_runway"],
        "delta": counter_move_result["p50_runway"] - baseline_runway,  # Compare vs baseline!
        "survival": counter_move_result["survival_18m"],
    }

# NOT this (broken):
# "delta": counter_move_result["p50_runway"] - current_sim_p50  # Wrong comparison!
```

Also: counter-moves should be CONTEXTUAL to the simulation scenario:
- If sim is about cost increases → counter-moves should include "negotiate supplier contracts", "switch carriers"
- If sim is about customer loss → counter-moves should include "loyalty program", "retention campaign"
- If sim is about growth → counter-moves should include "expand channels", "raise prices"

## ADDITIONAL QUICK FIXES

### Simulation Engine Intermittent Availability
The simulation engine sometimes returns "temporarily unavailable" errors. Add retry logic:

```typescript
// Frontend: retry simulation with exponential backoff
async function runSimulation(query: string, retries = 3): Promise<SimResult> {
  for (let i = 0; i < retries; i++) {
    try {
      const result = await fetch('/api/simulate', {
        method: 'POST',
        body: JSON.stringify({ query }),
        signal: AbortSignal.timeout(120000), // 2 min timeout
      });
      if (result.ok) return result.json();
      if (result.status === 503) {
        await new Promise(r => setTimeout(r, 2000 * (i + 1))); // Backoff
        continue;
      }
      throw new Error(`Simulation failed: ${result.status}`);
    } catch (e) {
      if (i === retries - 1) throw e;
    }
  }
}
```
